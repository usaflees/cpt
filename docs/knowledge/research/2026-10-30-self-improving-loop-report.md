# Collect privately, ship slowly, measure honestly

The most efficient, reliable and free way to start a self-improving loop for cryptopriceticker.com is a four-stage pipeline: a **non-AI collector** pulls search and on-site data every night into **private storage**; once a week an agent reads only a **sanitized digest** and opens at most two **pull requests**; **deterministic CI plus a Cloudflare preview** gate every change; and an **experiment log** with per-page cooldowns decides what stays. Everything runs on free tiers plus the Claude subscription the owner already has. The right signals are **Google Search Console (GSC)**, the **URL Inspection API**, **Cloudflare Web Analytics** and **Cloudflare zone HTTP analytics**, pulled via GraphQL. GA4 is not one of them. Gemini picked a reasonable set of search signals, but the way it moves and reads them is broken. It commits competitive search data daily to the root of a **public** repo that Cloudflare Pages deploys, so the file would end up on GitHub, in permanent git history and at a live URL. Its `[skip ci]` suffix does not stop Pages, which only honors the flag as a prefix. Its 500-row cap throws away exactly the low-click rows that "striking distance" analysis needs. Its "CTR below 3%" rule flags nearly every result in positions 4–10, because the 2026 desktop average there is 0.5–1.7%. It also reads from a GA4 property that does not exist. The deeper limit is traffic. With 114 coin pages and little traffic, the loop's real value in the first months is **diagnosis**: indexing problems, 404s, Core Web Vitals and duplicate titles. Measured SEO "wins" will come slowly, and most experiments will end inconclusive. This week's job is setup done by hand and starting data collection, because history is the bottleneck. Agent autonomy comes after four to eight weeks of data.

## A four-stage loop where the agent never touches credentials

The architecture rests on one rule: the process that runs the language model never holds Google credentials, Cloudflare tokens or raw query strings. The evidence for this rule is concrete. In a June 2026 lab test, Microsoft showed an injected prompt making Claude read `/proc/self/environ` inside claude-code-action. The model obtained the API key and altered it so that GitHub's secret masking missed it ([Microsoft Security Blog](https://www.microsoft.com/en-us/security/blog/2026/06/05/securing-ci-cd-in-agentic-world-claude-code-github-action-case/)). Earlier exploits used issue titles and PR text against agents from every vendor, including PromptPwnd ([Aikido](https://www.aikido.dev/blog/promptpwnd-github-actions-ai-agents)) and Clinejection ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-clinejection-prompt-injection-cicd-cache-p)). GitHub's own Agentic Workflows design keeps write tokens and API keys out of the agent process entirely ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-ai-github-actions-security-20260503-csa-st/)). Search queries are attacker-controllable text, since anyone can make Google record a query. That makes "telemetry fed straight to an agent with write access" an injection channel, even though no incident of this exact type has been documented.

**Stage 1, collect (no AI).** A **Google Apps Script** bound to a private Google Sheet runs nightly on a time-driven trigger as the owner's own Google account. Because it runs as the owner, there is no service account, no JSON key and no GitHub secret. It also sidesteps a 2026 problem where Search Console's "Add user" screen rejects new service-account emails with "email not found" ([Search Central Community](https://support.google.com/webmasters/thread/429020059/unable-to-add-service-account-email-to-google-search-console?hl=en)). Search Console has no Apps Script advanced service, so the script calls the REST API with `UrlFetchApp` and `ScriptApp.getOAuthToken()`. The `webmasters.readonly` scope is declared in the manifest ([Apps Script advanced services](https://developers.google.com/apps-script/guides/services/advanced)). Consumer quotas allow 6 minutes per run, 90 minutes of trigger time and 20,000 URL fetches a day, which is far more than about ten calls a night ([Apps Script quotas](https://developers.google.com/apps-script/guides/services/quotas)). The same script calls Cloudflare's GraphQL endpoint with a read-only token kept in Script Properties.

Each night it pulls one finalized day of GSC data rather than re-querying a 30-day window. Google advises against "requerying the same data", and notes that query-plus-page groupings are the most expensive ([GSC usage limits](https://developers.google.com/webmaster-tools/limits)). It runs three groupings: `[page]` for accurate totals, `[query,page]` for detail, and `[page,device]`. Each uses `rowLimit: 25000` and `startRow` pagination until a page comes back empty ([GSC: getting all your data](https://developers.google.com/webmaster-tools/v1/how-tos/all-your-data)). It also inspects about 40 URLs a day through the URL Inspection API, cycling all 115 every three days against a 2,000-per-day quota. It stores only *changes* in `coverageState` and `googleCanonical` ([index.inspect](https://developers.google.com/webmaster-tools/v1/urlInspection.index/inspect); [limits](https://developers.google.com/webmaster-tools/limits)). From Cloudflare it reads three things: `rumPageloadEventsAdaptiveGroups` for views and visits by path, device and referrer; `rumWebVitalsEventsAdaptiveGroups` for p75 LCP, INP and CLS; and `httpRequestsAdaptiveGroups` for 404s and 5xx errors by path. The RUM datasets need only an *Account Analytics Read* token ([Cloudflare token docs](https://developers.cloudflare.com/analytics/graphql-api/getting-started/authentication/api-token-auth/)). Snapshotting every night matters because Cloudflare down-samples RUM to about 10% after seven days ([Web Analytics FAQ](https://developers.cloudflare.com/web-analytics/faq/)), and Free-plan HTTP analytics keep only 31 days ([Cloudflare changelog, Oct 2026](https://developers.cloudflare.com/changelog/post/2026-10-02-30-days-analytics-on-every-plan)). The script can also email the owner on deterministic health alarms, such as a new 404 path or a page dropping out of the index, without any AI involved.

**Stage 2, store privately.** Raw tabs stay in the private Sheet, which both Claude's Drive connector and Gemini's `@Google Drive` can read ([Claude Drive connector](https://claude.com/docs/connectors/google/drive); [Gemini Workspace app](https://support.google.com/gemini/answer/15229592?hl=en)). Once a week the script also writes a **sanitized digest** to a new **private repo**, `usaflees/cpt-telemetry`, through the GitHub contents API. It uses a fine-grained token limited to that single repo. The digest holds page-level numbers only: impressions, clicks, impression-weighted position, CTR, p75 vitals, 404 counts and index-state changes. Query text is reduced to terms that match an allowlist built from `assets/coins.js` (names and tickers) plus intent words such as "price", "chart" and "market cap". Everything else is counted as "other" and never passed through. This follows OWASP's least-privilege advice and OpenAI's advice to "extract only specific structured fields" from untrusted input ([OWASP LLM01](https://owasp.org/www-project-top-10-for-large-language-model-applications/2_0_vulns/LLM01_PromptInjection.html); [OpenAI agent safety](https://platform.openai.com/docs/guides/agent-builder-safety)).

**Stage 3, propose (AI, weekly).** In Phase 1 the owner starts a Claude Code on the web session by hand each Monday, using a saved "weekly review" prompt. In Phase 2 that prompt becomes a **Claude Code cloud scheduled task** with a weekly preset or custom cron. It creates `claude/`-prefixed branches and can open PRs, using the owner's existing subscription ([Claude Code scheduled tasks](https://code.claude.com/docs/en/routines)). The agent edits a small **data file** that `scripts/build-coin-pages.mjs` reads, such as a per-coin `seo-overrides.json` holding title, description and H1. It does not hand-edit 114 HTML files. It must add an experiment-log entry and cite any earlier experiment on the same page.

**Stage 4, gate and measure (no AI).** Each same-repo PR branch gets a Cloudflare Pages preview at `<branch>.<project>.pages.dev`, and the Cloudflare GitHub App posts the link on the PR ([Pages preview deployments](https://developers.cloudflare.com/pages/configuration/preview-deployments)). Required checks run on the build and on that preview. The owner merges by hand. On the fixed evaluation date, a script rather than the LLM computes the result and records keep, revert or iterate.

| Need | Tool that fits | Why this one | Free-tier headroom |
|---|---|---|---|

| Second opinion (optional) | Gemini (`run-gemini-cli@v0`, or a manual paste) as PR reviewer | A different model family makes correlated errors less likely | Free tier |

The fallback collector, for an owner who prefers everything in git, is a scheduled GitHub Action **inside the private repo**. It authenticates to Google through Workload Identity Federation (WIF) with a service account, which Google's own auth action recommends over JSON keys ([google-github-actions/auth](https://github.com/google-github-actions/auth)). This route inherits the service-account "Add user" problem, and its documented workaround makes the service account a verified *owner*, which widens the blast radius. Apps Script avoids both problems, which is why it is the default here.

## This week is setup by hand; agent autonomy waits for data

The loop cannot propose anything useful until data exists, and three of its sources keep only short histories: RUM for 7 days unsampled, HTTP analytics for 31 days, and GSC for 16 months. So the first job is to start collecting. A live check during research found **no Cloudflare beacon** in the page HTML and no CSP header on the live response. QA traced this to the simplest cause: `main` is still the pre-optimization commit, and the new `_headers`, coin pages and sitemap live only on the unmerged `claude/static-html-optimization-aalhzo` branch. **Merging that branch is step zero.** The repo also has **no `.github/workflows` directory and no `package.json`** today, so the CI described below is new work, not a tweak to something that exists.

**Cadence: collect nightly, analyse weekly, change rarely.** GSC data lands in 2–3 days and the last two days may be preliminary ([About Search Console data](https://support.google.com/webmasters/answer/96568?hl=en)). Google says to "wait a few weeks to assess whether your work had beneficial effects" ([SEO Starter Guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide)). Title changes usually show in 1–2 days but can take weeks to months, according to secondary reporting of a 2026 Google talk ([Search Engine Journal](https://www.searchenginejournal.com/google-crawling-indexing-recovery-timing-ranges/591829)). A daily agent would mostly re-read the same noisy, partly provisional data and churn pages. Health alarms can be daily, because they are deterministic and change nothing.

## Gemini's plan collects the right signals but leaks and misreads them

Gemini correctly identified GSC as the primary signal, nightly automation as the delivery model, and an Apps Script plus Sheet as a no-infrastructure alternative. The defects sit in how the data is stored, published, filtered and interpreted. There is also a structural gap: both of its options stop at producing a context file. Nothing *proposes*, gates, ships or measures a change, so neither option is yet a self-improving loop.

| # | Gemini claim | Verdict | Why | Fix |
|---|---|---|---|---|
| 1 | Commit `AI_TELEMETRY_CONTEXT.md` to the repo root daily | **Wrong, unsafe** | `usaflees/cpt` is public, and Pages deploys the repo root. The existing `_headers` already marks `README.md`, `/docs/*` and `/scripts/*` noindex because they are being served. The file would be readable on GitHub, kept in git history forever, and live at `/AI_TELEMETRY_CONTEXT.md` after the next normal deploy. Query and landing-page data is competitive intelligence ([Pages build config](https://developers.cloudflare.com/pages/configuration/build-configuration/index.md); [GitHub artifacts on public repos](https://docs.github.com/actions/managing-workflow-runs/downloading-workflow-artifacts)) | Private Sheet plus private repo. Later, move the site into `public/` as the build output directory so non-site files stop being served |
| 2 | `chore(telemetry): … [skip ci]` stops rebuilds | **Wrong for Pages** | Pages honors only `[CI Skip]`, `[CI-Skip]`, `[Skip CI]`, `[Skip-CI]` and `[CF-Pages-Skip]`, case-insensitive, **as a prefix** ([Pages GitHub integration](https://developers.cloudflare.com/pages/configuration/git-integration/github-integration/)). A suffix triggers a daily build. A skip also never keeps the file private | Moot once telemetry leaves the repo. If ever needed, start the message with `[skip ci]` |

A 500-row cap drops the zero-click rows that striking-distance analysis looks for, and gives no sign that it did. Query+page groupings "may drop some data", so totals need a `[page]`-only pull ([query reference](https://developers.google.com/webmaster-tools/v1/searchanalytics/query); [all your data](https://developers.google.com/webmaster-tools/v1/how-tos/all-your-data)) | `rowLimit` 25000 with `startRow` pagination, plus `[page]` and `[page,device]` pulls |
| 8 | Window "last 30 days to 2 days ago", re-queried nightly | **Partly correct** | Data is "typically available after 2-3 days", so the window is silently short or provisional. Re-querying the same 30 days of query+page data is the load pattern Google tells you to avoid ([limits](https://developers.google.com/webmaster-tools/limits)) | Pull one final day each night, detecting the latest final date first, and aggregate locally with impression weights |
| 9 | "Striking distance" = position 8–20, top 20 by impressions | **Partly correct (heuristic)** | Practitioners disagree on the band (8–20, 11–20, 11–30) and it has never been validated. Average position blends devices and countries ([GSC position definition](https://support.google.com/webmasters/answer/7042828)). On the 2026 AWR desktop curve, moving from position 12 (0.70%) to 8 (0.47%) gains nothing; only the top 3 pays ([AWR CTR study](https://www.advancedwebranking.com/seo/organic-ctr)) | ≥100 impressions per row, the lead page per query, a cannibalization flag (home vs `/coin/btc/`), and a score of impressions × (expected CTR at target − current CTR) using **the site's own curve** |
| 10 | "CTR bleeders": position ≤10, ≥50 impressions, CTR <3% | **Wrong** | On AWR's July 2026 desktop data, positions 4–10 average **0.46–1.71% CTR**, so the rule flags nearly every row as "bleeding". At 50 impressions, 0 clicks has a 95% Wilson upper bound of about 7%, and 1 click about 10.5% (our calculation), so the rule cannot tell a weak snippet from noise. AI Overviews alone cut position-1 CTR by roughly half, and Google's own price boxes on "[coin] price" queries likely depress it further (unverified) ([AWR](https://www.advancedwebranking.com/seo/organic-ctr); [Ahrefs](https://ahrefs.com/blog/ai-overviews-reduce-clicks-update)) | Compare against the site's own CTR at the same position band, require ≥200–300 impressions or a Wilson bound, and segment by device. Google's bubble chart uses the site's own averages as quadrant lines ([Google bubble chart](https://developers.google.com/search/docs/monitor-debug/bubble-chart-analysis)) |
| 11 | GA4 `runReport` (pagePath, deviceCategory, views, users, engagementRate, avgSessionDuration) | **Wrong for this site** | No GA4 property exists. Adding one needs Google tag hosts in the CSP ([Google tag CSP](https://developers.google.com/tag-platform/security/guides/csp)), probably an EEA consent banner ([CNIL](https://www.cnil.fr/en/sheet-ndeg16-use-analytics-your-websites-and-applications)), and contradicts the site's privacy positioning. Engagement rate is a weak target on a glance-and-go ticker | Use Cloudflare RUM instead: `count` for views, `sum.visits`, `deviceType` and `requestPath`. Drop session metrics |
| 12 | Option B: Apps Script plus "Site_SEO_Telemetry_Live" Sheet, read via `@Google Drive` | **Largely correct**, and the better of Gemini's two options | Runs as the owner, nothing public, within quota. Gemini can read Sheets ([Gemini Workspace app](https://support.google.com/gemini/answer/15229592?hl=en)). Its STRIKING_DISTANCE and LOW_CTR_TITLE_FIX tags inherit the flaws in rows 9 and 10, and Search Console needs `UrlFetchApp` because no advanced service exists | Adopted as Stage 1, with corrected thresholds, Cloudflare data added, link sharing off, and a sanitized weekly digest |
| 13 | Third-party MCP connectors (Sequel.sh, Windsor.ai, PaidSync, community `mcp-google-search-console`) | **Risky for an unattended loop** | No official Search Console MCP server exists. Several community servers request the full `webmasters` write scope and none is reviewed by Google ([LukeRenton repo](https://github.com/LukeRenton/google-search-console-mcp); [mcp.so listing](https://mcp.so/servers/mcp-gsc)). Hosted SaaS connectors put a third party between the agent and the data. They were not evaluated, and no sponsored sources are used | Use them, if at all, in interactive owner-present sessions with read-only scope. Google's official GA4 MCP server is read-only but irrelevant without GA4 ([GA MCP](https://developers.google.com/analytics/devguides/MCP)) |
| 14 | Nightly cadence for the AI context | **Partly correct** | Nightly *collection* is right because RUM and HTTP data age out. Nightly *analysis* churns on provisional data | Collect nightly, analyse weekly, enforce a 28–42 day per-page cooldown |

## Four QA passes reshaped the recommendation

The first draft of this strategy was simpler: one GitHub Action in the public repo pulling GSC and Cloudflare data, plus a nightly Claude run that edited HTML. Four review passes changed it, and each change is traceable to a specific finding.

| Pass | What it checked | What it found | What changed |
|---|---|---|---|
| **1. Security and privacy** | Where every credential lives; what the agent process can read; injection channels; public exposure; connectors; branch-protection bypass; EU consent | (a) Any secret in a public repo's agent job can be exfiltrated through an injected prompt (the Microsoft and Clinejection cases above). (b) Cloud scheduled tasks **include all connected MCP connectors by default, writes included**, and run in auto mode ([scheduled tasks](https://code.claude.com/docs/en/routines)). This account has Gmail, Google Drive (with share and trash tools) and a **Coinbase trading** connector attached. (c) Scheduled-task commits carry the owner's GitHub identity, so rules the owner can bypass do not bind the agent. (d) Pages previews are public by default ([previews](https://developers.cloudflare.com/pages/configuration/preview-deployments)). (e) Public-repo issues are an extra injection channel | Collector moved to a non-AI Apps Script. Telemetry moved to private storage. Query text reduced to allowlisted terms. Agent output constrained to a schema-validated data file. **Every connector stripped from the task.** Ruleset set to "do not allow bypass". The agent is never triggered from issues or comments. Data branches excluded from previews. The privacy page discloses cookieless analytics |
| **2. Feasibility and statistics** | Data volume at low traffic; sampling; anonymization; minimum detectable effect; confounders; regression to the mean | (a) RUM on small sites comes back with `sampleInterval` around 10–20 ([DEV, Aug 2026](https://dev.to/robertcasschdot/your-cloudflare-analytics-are-rounded-to-the-nearest-10-and-the-api-will-tell-you-so-10nn)). (b) Rare queries are anonymized and missing from rows ([performance data deep dive](https://developers.google.com/search/blog/2022/10/performance-data-deep-dive)). (c) CrUX probably returns no data for this origin. (d) Split testing typically needs hundreds of pages per template and ~30k organic sessions a month ([SearchPilot](https://www.searchpilot.com/resources/blog/what-is-seo-split-testing)); 57 pages per arm can detect only very large effects. (e) Picking the worst pages guarantees some apparent "improvement" on its own. (f) Crypto news spikes swamp per-coin metrics | Primary metric switched to **impressions**, with CTR compared only within the same position band. Impression floors and Wilson bounds added. Plain before/after replaced with a randomized, impression-matched control group chosen *after* candidate selection. A/A placebo required before the first test. Coins with news spikes excluded. Hygiene fixes logged as "unmeasured rollouts". Agent cadence changed from nightly to weekly |
| **3. Cost and maintenance** | Every free-tier limit; silent failure modes; credential expiry; upkeep burden | (a) Pages Free allows 500 builds a month and one concurrent build ([Pages limits](https://developers.cloudflare.com/pages/platform/limits/)), ample for weekly PRs. (b) A public repo's scheduled Action is disabled after 60 days without activity ([GitHub events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)). (c) A scheduled task turns off if the GitHub connection stays expired for 72 hours. (d) Service-account keys never expire but can be auto-disabled if leaked. (e) Bing SOAP endpoints are dead. (f) Scheduled-task limits are hourly (100 runs per hour per account) on top of normal subscription usage | Apps Script chosen as collector, so there are no keys to rotate and no 60-day trap. | **4. Search-policy compliance** | Whether automated edits to 114 templated pages could trigger Google's spam or helpful-content signals | Google names "using generative AI tools… to generate many pages without adding value" as scaled content abuse ([spam policies](https://developers.google.com/search/docs/essentials/spam-policies)). A final pass re-read the recommendation as a whole and checked it against the owner's constraints: free, efficient and reliable. The Phase 2 CI list is the largest new effort, at roughly a day of Claude-assisted work. It was kept because, with human merge, it is the only thing between a hijacked agent and production. Its scope was capped at checks that need no paid services.

## With 114 pages, most experiments will end inconclusive

The loop will not find statistically clean SEO wins quickly. Airbnb needed about **100,000 URLs** to reach 80% power for 2% effects ([Airbnb Engineering](https://medium.com/airbnb-engineering/experimentation-measurement-for-search-engine-optimization-b64136629760)). Etsy needed groups of **1,000 pages each** ([Etsy](https://www.etsy.com/codeascraft/seo-title-tag-optimization)). SearchPilot says a site with 60 sessions a day is "never close to" what is required ([SearchPilot](https://www.searchpilot.com/resources/blog/a-year-of-seo-testing-with-searchpilot)). At about 57 pages per arm, only changes on the order of tens of percent or more will separate from noise. The honest way to learn this site's detectable effect is to simulate placebo splits on its own GSC history once eight to twelve weeks have accumulated. The common outcome will be "inconclusive". The rule for that outcome is to keep a change only when it is also a best-practice improvement, and otherwise revert it.

What the loop *can* do well, starting in week one, is diagnosis:

- coin pages that Google crawled but did not index, or that it consolidated under another canonical;
- duplicate or boilerplate titles across the 114 pages;
- 404s from renamed tickers;
- Core Web Vitals regressions after a deploy;
- queries where the home page and a coin page compete with each other.

It can also keep an honest record of every change, so that later traffic gains can be attributed. What it cannot do is reliably attribute small ranking moves to its own edits, beat Google finance widgets and AI Overviews on head terms like "bitcoin price", or substitute for links and genuinely unique data. Google itself warns against "quick fix" changes ([core updates](https://developers.google.com/search/docs/appearance/core-updates)).

Several prerequisites remain manual because no agent can do them for the owner:

- Search Console Domain verification through DNS.
- Approving the Apps Script OAuth scopes.
- Creating the Cloudflare analytics token and choosing EU coverage.
- Creating the private repo and the fine-grained GitHub token.
- Installing the Claude GitHub App and configuring the ruleset.
- Confirming that the live deployment matches the repo.
- Merging every PR.

The second site, Ground Zero Veterans Outreach, can reuse the same collector with a second property list, but it needs its own digest and experiment log, and none of this research examined its stack.

## Conclusion

The single biggest risk in Gemini's plan is where the data goes: competitive search data published daily to a public repo that is also the website's deploy root. The analytics questions are secondary to that. Once data and credentials are kept away from both the public repo and the model, the remaining design choices become low-risk and cheap. Collect everything nightly with a dumb script, let the agent see only numbers attached to known coin names, and make every change pass through a preview, deterministic checks and a human merge.

The honest framing for a young, low-traffic site is to build a **self-auditing website first and a self-optimizing one later**. In the first months the loop earns its keep by catching indexing gaps, broken links, regressions and duplicate titles, which are real problems with unambiguous fixes. It also builds the daily history and experiment record that make attribution possible once traffic grows. Optimizing CTR and rankings becomes worthwhile only once the site's own data can show what a "normal" CTR at each position looks like. That is a matter of months, and starting collection this week is what shortens the wait.
